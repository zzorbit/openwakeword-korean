# 설치·실행 검수 기록

이 문서는 **라이브러리 기능이 작동하는지 확인한 범위**를 설명합니다. 호출어를 얼마나 잘 인식하는지는 별도의 모델 평가 결과로 확인합니다.

## 확인한 기능

| 영역 | 확인 내용 |
| --- | --- |
| 설치 | 별도 폴더에 설치한 패키지로 명령과 API 실행 |
| 음성 생성·검수 | 합성 음색 재사용, 호출어 단독 생성, 검수 결과 저장, 중단 후 이어 생성 |
| 공개 자료 | 다운로드 재개, 파일 크기·해시 확인, 손상 파일 거부 |
| 데이터 준비 | 학습·평가 자료 분리, 승인 자료 확인, 원본 수 × 증강 횟수 검증 |
| 학습 | 작은 시험 자료로 실제 학습, 중단·재개, ONNX 모델 파일 생성 |
| 평가 | 감지 기준 비교, 최종 평가 잠금, 실제 채점 오디오와 결과 화면의 일치 |
| 표본 모델 | 제공 모델 파일의 해시와 호출 결과 재현 |
| 결과 사이트 | 오디오 연속 재생, 소음 수준 선택, 일시정지 |

## 0.14.2 결과 화면의 표현과 비교 표

- 소음별 표의 모델·울림 선택, 0%·시험 안 함·결과 없음 구분, 실제 실행 모델 이름, 대용량 페이지 이동과 연속 재생을 검증했습니다. 화면 문구는 소규모·대규모 화면에서 같은 모듈을 사용합니다.

## 0.14.1 큰 결과 화면

- 112,137개 결과의 기존1.12GB 브라우저 스크립트로 인한 충돌을 조사하고, 전체 목록과128개 단위 상세 페이지로 나누는 화면을 추가했습니다. 전체 상세 결과는 브라우저에 한꺼번에 적재하지 않으며 최근2페이지만 보관합니다.
- 관련 Python 검사59개와 웹 검사73개를 통과했습니다. JSON 스트리밍·분할 조건·실제 점수와 WAV 보존·표시 범위·연속 재생·늦은 응답·캐시 제한을 확인했습니다. 보관 실험 스크립트가 필요한 로컬 비교2개는 제외했습니다.
- 실제112,137개 기록을 화면용으로 변환한 뒤 브라우저에서 처음·마지막 원본 이동과 자동 갱신 상태를 확인했습니다. 초기 데이터는 약13.8MB, 상세 페이지는 최대약220KB이며 전체 평가 기록을 줄이거나 다시 채점하지 않았습니다.

## 0.14.0 평가 화면과 GPU 기본값

- 현재 평가 작업의 로그 끝24KB만 읽어 음원 수와 게이지를 갱신합니다. 전체 단계 수, 평가 음원 수, 사전 검증과 결과 정리를 구분합니다. 파일 수로 긴 비호출 평가의 남은 시간을 임의 추정하지 않습니다.
- 실제 CUDA 세션을 별도 프로세스에서 확인한 새 Development 평가만 GPU를 우선 선택합니다. 사용할 수 없으면 CPU와 선택 사유를 기록하고, 기존 CPU/GPU 평가 재개 계약과 독립 Final의 CPU 기준은 유지합니다. FP32·TF32 비활성·경계 음원 전체 CPU 재확인은0.13.0과 같습니다.
- Windows x64·Python3.12의 격리 GPU 실행 도구는 프로젝트 캐시에 준비하고, 기본 CPU 패키지를 보존합니다. 설치 후 실제 CUDA 연산과 파일 해시를 확인합니다. 다른 플랫폼에서는 호환 GPU 런타임을 직접 연결할 수 있습니다.
- 관련 Python 검사300개와 웹 화면 검사61개를 통과했습니다. 해당 테스트 환경에서 CUDA를 요구하는1개는 건너뛰었고, 보관된 실험 스크립트가 필요한 로컬 비교2개는 제외했습니다. 별도 설치한0.14.0 wheel에서는 실제 CUDA 자동 선택과 실행을 확인했으며, MatMul·Conv의 CPU 대체 금지 시험도 통과했습니다. 두 실제 WAV의 기본 자동 평가에서도 GPU 경로·통계·결과 사이트 연결을 확인했습니다.

## 0.13.0 CUDA 배치 평가

- GPU 연산·CPU 완료분 이관·기존 CPU 평가·중단 재개·웹 단계와 작은 학습부터 결과 사이트까지 관련 검사215개를 통과했습니다. 격리 CUDA 환경에서 실제 경계 사례와 결과 사이트 통합 시험도 별도로 통과했습니다.
- CUDA는 FP32로 실행하며 TF32를 끕니다. GPU 점수와 CPU 점수가 비트 단위로 같다는 조건은 아닙니다. `evaluate --backend cuda --accept-gpu-numerical-differences`로 이 차이를 허용한 Development 평가만 실행합니다. 독립 Final은 기존 기준 연산과 잠금을 유지합니다.
- 원래 Mel 그래프의 배치 전체 최대값이 서로 다른 음원에 영향을 주는 문제를 재현했습니다. 원본 모델을 덮어쓰지 않고, 해시가 고정된 그래프에서 최대값과 하한 처리를 음원별로 분리한 메모리 사본을 사용합니다. 조용한 음원·큰 음원·무음의 CPU 배치 결과를 각 개별 CPU 결과와 비트 단위로 대조합니다.
- 기본 배치128, 경계 폭0.001입니다. 유효 프레임의 단일 모델 또는 평균 점수 하나라도 임계값과 이 범위 안에 있으면 음원 전체를 CPU로 다시 계산해 점수·감지·오호출·지연 기록을 대체합니다. 최대4개 CPU 프로세스가 이미 읽은 PCM을 사용하며 음원을 다시 다운로드하거나 F 드라이브에서 다시 읽지 않습니다. 이 경계 폭을 모든 입력의 오차 상한으로 주장하지 않습니다.
- 실제 경계 음원에서 GPU 프레임 하나의 임계값 통과 여부 차이를 확인했고, 이 경로의 CPU 재확인 후 전체 점수 비트와 판정이 CPU 기준과 같았습니다. 별도 ONNX Runtime GPU 패키지의 CPU 제공자도 기존 CPU 점수와 대조했습니다. 검증된 표본 밖의 완전한 수치 동일성을 뜻하지 않습니다.
- 기존 CPU 완료분을 재사용할 때는 원본 체크포인트·점수·검수 기록·모델·설정·manifest 해시와 완료 구간 순서를 검증해 별도 GPU 폴더로 복사합니다. CPU 원본은 보존하며 혼합 결과의 계보를 기록합니다. CPU 선행 검증 증빙이 있는 재개에서만 현재 출처·분할 메타데이터 검사와 남은 WAV의 사용 직전 해시·형식·구간 검사를 결합합니다. 새 평가의 전체 검증을 생략하지 않습니다.
- CUDA 실행에는 해당 ONNX Runtime GPU 패키지와 호환되는 CUDA/cuDNN, 그래프 변환용 `onnx`가 필요합니다. CPU 패키지와 충돌하지 않는 별도 실행 환경을 사용합니다. 별도 설치 경로는 `KOWW_GPU_RUNTIME_PATH`, DLL 디렉터리는 `KOWW_GPU_DLL_PATHS`로 지정할 수 있습니다. 실제 CUDA 제공자 생성에 실패하면 중단합니다.
- 실제512개 원본을4회 반복한2,048세션에서, 초기512개 이후1,536개 처리량은45.42세션/초였습니다. 총51.47초에는 초기화와 CPU 프로세스 종료가 포함되며,292개(14.26%)를 CPU로 재확인했습니다. 새 독립 음원2,048개를 검증한 결과나 전체 작업 시간 보장은 아닙니다. 별도 두 WAV로 실제 `evaluate`→점수 캐시·완료 receipt→결과 사이트도 실행해 CPU와 같은 통계·판정을 확인했습니다.

## 0.12.4 평가 효율 검증

- 중복 파일 검사 재사용, 파일 변경·손상 거부, Final 분리, 같은 점수와 재개 식별자, 실제 작은 학습→평가→사이트 흐름을 포함한 관련 검사116개를 통과했습니다. 신규 사이트 복사 검사와 기존 화면 범위 검사도 따로 확인했습니다.
- 실제64개 WAV를 반복한320세션에서 작업자4·8·11개의 모든 float32 점수와 감지 기록 해시가 같았습니다. 첫64세션 준비를 제외한 처리량은20.63·30.10·32.64세션/초였습니다. 별도 기존4개 작업자가 함께 실행 중이었으며, 이 작은 표본의 속도를 전체 평가 시간으로 사용하지 않습니다.
- 같은 평가 실행의 해시·오디오 정보만 재사용하고 실행 사이에는 다시 검사합니다. 캐시 후 변경과 읽는 도중 변경을 검사했으며, 결과 사이트는 원본1회 읽기·독립 복사본1회 읽기로 검증합니다. WAV 바이트·점수·JS 출력 형식은 유지했습니다.
- 별도 실험 환경에서 RTX4090·ONNX Runtime1.31·CUDA·FP32·TF32비활성으로 단일 프레임과 여러 독립 음원의 배치를 비교했습니다. 실험용 Mel 복사본의 배치 전체 최대값 처리를 음원별 최대값으로 바꾸어 음원 간 간섭을 제거했으며, 원본 모델은 변경하지 않았습니다. CPU 배치32·64·128은 실제512개 음원의26,996프레임에서 기존 CPU 점수와 비트 단위로 일치했습니다.
- 같은512개에서 GPU 배치128의 신경망 계산은4.44초, CPU 배치32는51.28초였습니다. 이는 전체 파일 검사·채점·사이트 생성 시간 비교가 아닙니다. GPU 점수에는 최대 약0.00003001 차이가 있었고 대표·경계 검사에서 최종 감지·성공·오호출·지연 차이는 관측되지 않았습니다. 경계128개에서는 임계값 통과 여부가 다른 프레임1개가 있었으므로, 전체 음원의 같은 결과를 보장하거나 GPU 점수를 기존 CPU 점수에 자동 혼합하지 않습니다. 이 GPU 실험은 제품의 정식 GPU 평가 경로 구현·검증 완료를 뜻하지 않습니다.

## 0.12.3 저장 용량 산정 검증

- 전체 자료를 다운로드하지 않고 기존 MUSAN·Zeroth 압축파일의 member 크기, 고정 catalog와 제공자 모델·자료 목록, 기존 설치 파일과 작은 직렬화·평가 fixture를 조사했습니다. 실제 파일 크기와 형식 계산, 작은 표본에만 해당하는 관측을 구분합니다.
- 상용 모델용의 부분 합계를 전체 필요량으로 표시하지 않으며, 미확정 값은 `null`로 유지합니다. 새 화면의 기준값·작업량 변경값을 Python 계산과 대조하고 손상된 계산 근거가 구형 예산으로 대체되지 않는지 검사합니다. 자세한 값과 조건은 [저장 용량 산정](STORAGE_POLICY.md)에 있습니다.
- 새 자료 생성·정식 재학습·전체 평가·Final 잠금 해제는 하지 않았습니다. 기존 모델과 학습·평가 정책은 보존합니다. 이전 절의 저장 예산은 해당 버전의 과거 기록이며 현재 권장 용량으로 사용하지 않습니다.

## 0.12.0 학습용 FLAC 보관 검증

- 별도 폴더에 설치한 wheel의 전체 기능 검사 **1,100개 통과**, Windows 링크 권한 관련 2개 생략, 내부 과거 구현 대조 5개 제외. 중단 재개·분할 순서 보완 후 최종 코드의 관련 검사 **316개 통과**, 권한 관련 1개 생략. 웹 UI **43개**, 마이크 UI **14개**도 통과했습니다.
- 48kHz·44.1kHz 24bit stereo FLAC과 24kHz PCM16 WAV에서 기존 전처리 WAV와 새 FLAC의 디코딩 PCM이 같았습니다. 원본 ID·원본 해시·자료 선정·분할·순서·할당량, 무음 구간의 소음 재선택, RIR 및 R1/R3/R5 증강 결과와 실제 frontend 특징도 대조했습니다.
- 같은 seed로 CNN128을 CPU에서 4회 학습한 두 모델의 가중치·optimizer·sampler·RNG 상태와 ONNX 해시가 같았고, 추론 점수와 감지 여부도 일치했습니다. 소규모 절차 검증이며 전체 규모 모델의 성능 재평가를 뜻하지 않습니다.
- 기존 실제 MLS 30개·FMA 원곡 1개·YODAS2 20개의 원본 **51개는 그대로 보존**했습니다. 변환 가능한 41개의 FLAC은 기존 PCM과 같았습니다. YODAS2 10개는 종전과 동일한 클리핑 검사에서 거부했으며 기준을 완화하거나 원본을 정리하지 않았습니다. 압축 표본 비율은 [저장 위치 안내](STORAGE_POLICY.md#실제-표본의-압축-크기)에 있습니다.
- 새 단독 소유 원본만 검증 후 정리하는지, 공유·외부·기존·불량 자료를 보존하는지, 원본 정리 도중 및 FLAC 게시 직후 중단에서 재개하는지 검사했습니다. 저장 공간·시스템 IO·해시 오류는 승인으로 바꾸지 않고 중단합니다. 기존 표본 모델 묶음 33개 파일도 이전 게시본과 같습니다.
- 설치판 HTTP와 실제 브라우저에서 새 저장 정책과 세 규모의 용량 표시를 확인했습니다. 상용의 **WAV 기준 참고 예산 약 1.447TB**에는 FMA 선택 원곡의 임시 공간 약 125GB가 포함됩니다. 전체 자료의 FLAC 크기는 아직 실측하지 않았고 다운로드 전송량은 바뀌지 않습니다.

상세 범위·해시는 [0.12.0 검증 기록](../validation/publication_checks_120.json)에 있습니다. 전체 10,000시간 수집·새 내용 승인·정식 성능 재학습·독립 Final 평가는 이번 변경에 포함하지 않습니다.

- 기존 보라야 평가 1,603개에서 단일 후보를 선택해 점수와 결과를 그대로 재사용했습니다. 실제 ONNX의 대표 200프레임에서도 점수와 감지 시각이 같았습니다. 운영 모델 선택이나 Final 승인을 바꾸지는 않았습니다.
- 대량 자료의 순차 처리 전후에 감사 결과와 Positive R1/R3·한국어 비호출 R1의 PCM·특징 파일·중단 후 재개 결과가 같았습니다. 기존 완료 캐시도 검증했습니다.
- Qwen 도구의 새 설치·import와 PyTorch/torchaudio 2.8.0 조합을 확인했습니다. 표본 모델·평가 WAV의 해시, 문서 링크, wheel·소스 압축 파일도 검사했습니다.

검증 범위와 수치는 [0.4.0 검증 기록](../validation/publication_checks_040.json)에 있습니다. 대규모 재학습이나 독립 최종 성능 시험을 새로 수행했다는 뜻은 아닙니다.

## 0.3.0 게시 전 결과

- 전체 기능 시험 **57개 통과**.
- 별도 폴더에 설치한 배포 패키지 시험 **54개 통과**. 개발 중 과거 구현과 비교하는 시험 3개는 이 설치 시험에서 제외했습니다.
- 공개 소음 파일의 실제 다운로드와 해시 확인, 예시 모델 파일 및 결과 사이트의 오디오 확인을 수행했습니다.

기계적으로 읽을 수 있는 기록은 [publication_checks.json](../validation/publication_checks.json)에 있습니다. 이후 커밋의 자동 검사 결과는 [GitHub Actions](https://github.com/zzorbit/openwakeword-korean/actions)에서 확인하세요. 자동 검사는 Python 3.12의 Windows·Linux 환경에서 실행합니다.

## 이 검사로 알 수 없는 것

작은 시험 자료로 학습이 끝났다는 사실만으로 새 호출어의 호출 성공률이 입증되지는 않습니다. 자동 검사에서도 대규모 TTS 생성이나 여러 사람의 실제 호출 시험을 매번 수행하지 않습니다.

표본 모델의 확인된 성능과 평가 범위는 [모델 설명서](../korean_openwakeword/resources/sample_chunsik/MODEL_CARD.md)에 있습니다. 새 호출어는 [학습 가이드](LIBRARY_GUIDE.md)의 개발용 평가와 독립 최종 평가를 진행하세요. OS·GPU·마이크가 달라진 환경의 결과는 해당 환경에서 확인해야 합니다.
